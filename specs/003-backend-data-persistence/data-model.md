# Data Model: Server Storage

**Feature**: 003-backend-data-persistence · Postgres (Neon) via Drizzle. Schema source: `server/db/schema.ts`. Migrations: `server/db/migrations/`.

All timestamps are `timestamptz` and returned as ISO-8601 strings. All ids are UUID v4 strings generated by the server, except where a restore keeps the original ids (research R12).

```text
couples 1──* media
couples 1──* rsvps
couples 1──* wishes
couples 1──* security_events
admin_sessions        (standalone; one admin)
throttles             (login + passcode lockouts)
rate_limits           (guest submission windows)
media_deletions       (provider files waiting to be deleted)
```

## couples

| Column | Type | Rules |
|---|---|---|
| `id` | uuid PK | |
| `slug` | text UNIQUE NOT NULL | `SLUG_PATTERN` (lowercase letters, digits and hyphens, 3–40 characters), not reserved (`isReservedSlug`). The same helpers as 002 in `src/data/slug.ts` |
| `status` | text NOT NULL | `'draft'` \| `'active'`, default `'draft'` |
| `default_theme` | text NOT NULL | CHECK `IN ('romantic-floral','elegant-classic','rustic-garden')`, matching `ThemeId` / `themeIdSchema` in `src/data/schema.ts` |
| `content` | jsonb NOT NULL | `WeddingContent`. Media are referenced as `media:<id>`. When it's validated, and how strictly, is listed under Rules below |
| `version` | integer NOT NULL | Starts at 1, +1 on every content, slug, theme or passcode change. Used for conflict detection (FR-005) |
| `passcode` | char(4) NOT NULL | `^\d{4}$`. Random on create or v1 import unless given |
| `passcode_version` | integer NOT NULL | Starts at 1, +1 when `passcode` changes. Embedded in couple access cookies (research R7) |
| `restore_pending` | boolean NOT NULL default false | True between import start and finish (research R12). Such a couple cannot be set Aktif |
| `created_at`, `updated_at` | timestamptz NOT NULL | |

**Status transitions**

```text
          create / duplicate / import
                    │
                    ▼
   ┌──────────►  draft  ───── setStatus('active') ─────►  active
   │                          requires: content passes full schema,
   │                          restore_pending = false,
   │                          all referenced media ready
   └──────────── setStatus('draft') ◄──────────────────────┘
```

**Rules**:
- **Conflict check.** An update runs `WHERE id = $id AND version = $expected`. If no row matches, the server returns 409 `conflict`.
- **Slug changes.** `slug` may change, and old links then 404 (spec edge case). A unique-constraint violation returns 409 `slug_taken`. A reserved slug returns 422 `slug_reserved`.
- **Content validation.** Drafts may be unfinished, as in 002, so how strictly content is checked depends on the action:

  | Action | Content check |
  |---|---|
  | `create`, `duplicate`, import | Structure only, with the `storedContentSchema` moved out of `src/data/backup.ts` into `src/data/schema.ts`: cover, couple, events and closing are present. A couple created from nicknames only is accepted |
  | `PATCH` (editor "Simpan") | Full `weddingContentSchema`, the same rules the editor form already requires before it saves (002 FR-012) |
  | `setStatus('active')` | Full `weddingContentSchema`. On failure: 422 `not_publishable` with the first problem (`firstContentProblem`) as the message. This is stricter than 002, which published without checking, and it stops guests from seeing a broken invitation |

- **Media references.** For every action, each `media:<id>` must belong to this couple and have `status = 'ready'` (FR-015).
- **Deleting.** Deleting a couple removes its `media`, `rsvps`, `wishes` and `security_events` rows (`ON DELETE CASCADE`). Its provider files are first written to `media_deletions` (FR-013).
- **Never sent publicly.** `passcode`, `passcode_version` and `restore_pending` never appear in public or couple-facing responses.

## media

| Column | Type | Rules |
|---|---|---|
| `id` | uuid PK | Keeps the original id on restore |
| `couple_id` | uuid FK → couples ON DELETE CASCADE | |
| `kind` | text NOT NULL | `'image'` \| `'audio'` |
| `mime` | text NOT NULL | image: `image/webp`, `image/jpeg`, `image/png` (photos are re-encoded in the browser). audio: any `audio/*`, matching the dashboard's file picker (e.g. `audio/x-m4a` on Windows) |
| `size` | integer NOT NULL | Bytes. image ≤ 10 MB, audio ≤ 10 MB (002 limits, FR-012) |
| `width`, `height` | integer NULL | Images only |
| `provider_key` | text NOT NULL UNIQUE | e.g. `wedding/prod/<coupleId>/<mediaId>` |
| `url` | text NULL | Delivery URL, set when `ready` |
| `status` | text NOT NULL | `'pending'` \| `'ready'` |
| `created_at` | timestamptz NOT NULL | |

**Status transitions**: `pending` → `ready` when the provider's signed upload result is verified (research R9). A `pending` row older than 24 h is deleted by the cron, along with any provider file.

**Limits checked when a couple is saved**: at most 30 gallery images (002 FR-016), at most 1 music file referenced.

**Usage figure (FR-014)**: the server reads the provider's usage (Cloudinary credits used / limit). With the local media driver it uses `sum(size)` against a 1 GB nominal limit. A warning flag is set at ≥ 80%.

## rsvps

| Column | Type | Rules |
|---|---|---|
| `id` | uuid PK | |
| `couple_id` | uuid FK → couples ON DELETE CASCADE | Couple must be `active` at submit time (US5-7) |
| `visitor_hash` | text NOT NULL | HMAC of the `wv` cookie (research R8) |
| `name` | text NOT NULL | Trimmed, 2–60 characters (`validateName`, `src/lib/validation.ts`) |
| `attendance` | text NOT NULL | `'hadir'` \| `'tidak_hadir'` (existing `Attendance` type) |
| `guest_count` | smallint NOT NULL | 1–5 when `hadir`, 0 when `tidak_hadir` (existing rule in `memory.ts`) |
| `submitted_at` | timestamptz NOT NULL | First submission |
| `updated_at` | timestamptz NOT NULL | Last replacement |

**Unique** `(couple_id, visitor_hash)`. A repeat submission upserts (FR-017).

**Totals** (US5-5): `attending = count(attendance='hadir')`, `notAttending = count(attendance='tidak_hadir')`, `people = sum(guest_count)`.

## wishes

| Column | Type | Rules |
|---|---|---|
| `id` | uuid PK | |
| `couple_id` | uuid FK → couples ON DELETE CASCADE | Couple must be `active` at submit time |
| `visitor_hash` | text NULL | NULL for seeded or restored wishes |
| `name` | text NOT NULL | 2–60 characters |
| `message` | text NOT NULL | 3–500 characters (`MESSAGE_MIN`/`MESSAGE_MAX`), stored and shown as plain text |
| `attendance` | text NULL | Optional, as in the existing `WishInput` |
| `hidden` | boolean NOT NULL default false | Set by the admin (FR-019) |
| `created_at` | timestamptz NOT NULL | |

**Index** `(couple_id, created_at DESC, id DESC)` for public pages of 20, newest first (FR-018). The cursor is `<created_at>|<id>` in base64url.

## admin_sessions

| Column | Type | Rules |
|---|---|---|
| `token_hash` | text PK | SHA-256 of the 32-byte cookie value |
| `created_at` | timestamptz NOT NULL | |
| `expires_at` | timestamptz NOT NULL | `created_at + 7 days`, absolute (FR-008) |
| `user_agent` | text NULL | Informational |

Deleted on logout. Expired rows are deleted by the cron.

## throttles

| Column | Type | Rules |
|---|---|---|
| `key` | text PK | `login:admin` or `passcode:<coupleId>` |
| `failures` | smallint NOT NULL | Consecutive failures |
| `locked_until` | timestamptz NULL | |

**Rules**:

| Key | Lockout | Message |
|---|---|---|
| `login:admin` | 5 failures → 60 s | "Terlalu banyak percobaan. Coba lagi dalam {n} detik." |
| `passcode:<id>` | 5 failures → 15 min (FR-010d) | "Terlalu banyak percobaan. Coba lagi dalam {n} menit." |

- During a lockout, the credentials are not checked at all.
- A success resets the counter. Reaching a lockout also resets it, after recording the lock.

## security_events

| Column | Type | Rules |
|---|---|---|
| `id` | bigserial PK | |
| `kind` | text NOT NULL | `'passcode_lockout'` (`'login_lockout'` has `couple_id` NULL) |
| `couple_id` | uuid NULL FK → couples ON DELETE CASCADE | |
| `created_at` | timestamptz NOT NULL | |

`CoupleSummary.accessWarning = true` when the couple has ≥ 3 `passcode_lockout` events in the last 24 h (FR-010d). Rows older than 30 days are deleted by the cron.

## rate_limits

| Column | Type | Rules |
|---|---|---|
| `bucket` | text PK | `wish:<coupleId>:<visitorHash>`, `rsvp:<coupleId>:<visitorHash>`, `ip:<coupleId>:<ipHash>` |
| `window_start` | timestamptz NOT NULL | Fixed 10-minute window |
| `count` | integer NOT NULL | |

Limits per window: wish 5, rsvp 5, ip 30 (research R8). Going over returns 429 "Terlalu banyak pesan, coba lagi nanti". The cron deletes stale rows.

## media_deletions

| Column | Type | Rules |
|---|---|---|
| `provider_key` | text PK | A single file, or a prefix ending in `/` (couple delete) |
| `resource_type` | text NOT NULL | `'image'` \| `'video'` \| `'prefix'` |
| `attempts` | smallint NOT NULL default 0 | |
| `created_at` | timestamptz NOT NULL | |

An immediate deletion is attempted after the database transaction commits, and the row is removed on success. Any row still here is retried by the daily cron (research R9).

## Shared TypeScript types (frontend ↔ server)

These go in `src/data/types.ts` and `src/services/types.ts`, imported by both `src/` and `server/`:

```ts
// additions to existing Couple / CoupleSummary
interface Couple { /* existing fields */ passcode: string }   // admin responses only
interface CoupleSummary { /* existing fields */ accessWarning: boolean; restorePending: boolean }

/** What the public site receives: media already resolved to absolute URLs. */
interface PublicCouple { slug: string; defaultTheme: ThemeId; content: WeddingContent }

/** Shown on the passcode screen and before unlock. */
interface CoupleGate { names: string; status: CoupleStatus; unlocked: boolean; retryAt: string | null }

interface RsvpRecord { id: string; name: string; attendance: Attendance; guestCount: number; submittedAt: string; updatedAt: string }
interface RsvpTotals { attending: number; notAttending: number; people: number }
interface WishRecord extends Wish { hidden: boolean }   // admin view; createdAt travels as ISO string
interface Page<T> { items: T[]; nextCursor: string | null }
```

## Validation sources (single source of truth)

| Rule | Shared code used by browser and server |
|---|---|
| Content rules (events, times, alt text, account digits) | `weddingContentSchema` in `src/data/schema.ts` |
| Slug format and reserved names | `src/data/slug.ts` |
| RSVP and wish fields | `src/lib/validation.ts` (`NAME_MAX` 60, `GUESTS_MIN/MAX` 1–5, `MESSAGE_MAX` 500) |
| Media limits | `MAX_UPLOAD_BYTES` (now in `src/admin/media/compressImage.ts`), moved to `src/data/mediaLimits.ts` so the server can import them |
| Passcode | `^\d{4}$` in `src/data/passcode.ts` (+ `randomPasscode()`) |
